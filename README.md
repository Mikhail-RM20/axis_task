# Сервис бронирования столиков в ресторане

Бэкенд сервиса бронирования столиков, реализованный на **Python 3.13** с использованием **FastAPI**, **SQLAlchemy 2.0 (async)**, **SQLite** и **Alembic**. Проект предоставляет REST API для создания бронирований, просмотра списка броней (с необязательной фильтрацией по дате), получения брони по ID и отмены брони без физического удаления записи. Валидация входных данных включает проверку имени гостя, формата номера телефона (`+7XXXXXXXXXX`), даты (от сегодняшнего дня до +30 дней), дискретных временных слотов (целые часы с `12:00` до `22:00`) и количества гостей (`1–10`).

---

## Принятые архитектурные решения

* **Конфигурация через `pydantic-settings` (`ConfigSetting`)**: параметры подключения к базе данных вынесены в класс настроек с кешированием через `@lru_cache` и значением по умолчанию (`bookings.db`). Это избавляет от хардкода путей в коде, позволяет при необходимости переопределять имя файла БД через `.env`, но при этом даёт проекту запускаться «из коробки» без обязательного создания `.env`. Так же для дальнейшего расширения в сторону PostgreSQL позволит управлять переменными окружения.
* **Асинхронная работа с БД и миграции Alembic**: вместо хранения данных в оперативной памяти выбрана реляционная база SQLite с асинхронным драйвером `aiosqlite` и ORM `SQLAlchemy 2.0`. Схема базы управляется через миграции **Alembic**, что позволяет безопасно развивать структуру таблиц без потери данных и воспроизводить схему на любом окружении одной командой `alembic upgrade head`.
* **Нормализация данных (`Person` и `Booking`) и защита от двойного бронирования**: данные гостя (`person`) и параметры брони (`booking_table`) разделены на две связанные таблицы. Перед созданием записи сервис в рамках одной транзакции (`flush` → `commit`) проверяет отсутствие активной брони (`status = active`) на выбранные дату и время, возвращая `409 Conflict` при попытке занять слот повторно. Отменённая бронь переводится в статус `cancelled`, остаётся в истории БД и освобождает слот для новых гостей.
* **Разделение входных и выходных Pydantic-схем**: выходная схема `BookingCreateOut` намеренно не унаследована от входной `BookingCreateIn`. Валидаторы на «не в прошлом» и «не дальше 30 дней» применяются только к новым входящим заявкам, чтобы чтение исторических или прошедших броней через `GET /bookings` не вызывало ошибок валидации ответа.
* **Слоистая архитектура, контроль качества и изоляция тестов**: приложение разделено на независимые слои (`routes`, `services`, `schemas`, `database`, `core`). Для поддержания чистоты кода и строгой типизации настроены **Ruff** и **Mypy** (`pyproject.toml`), а интеграционные тесты на **Pytest** разделены на позитивные и негативные сценарии и используют изолированную базу `SQLite :memory:` с подменой зависимости `get_db`.

## Что доделал бы при наличии времени

* Перевёл бы базу данных на **PostgreSQL** (`asyncpg`) с составным частичным уникальным индексом (`UNIQUE (booking_date, booking_time) WHERE status = 'active'`) для защиты от гонки запросов (Race Condition) на уровне СУБД и упаковал бы сервис в **Docker Compose**.
* Добавил бы сущность столиков с разной вместимостью (на 2, 4, 6 персон), чтобы система могла принимать несколько параллельных броней на одно время на разные свободные столы.
* Реализовал бы пагинацию (`limit` / `offset`) для эндпоинта `GET /bookings` и фоновые SMS/Telegram-уведомления с напоминанием о визите.

## Предварительные требования для запуска проекта

* **Python 3.11+** (разрабатывалось и тестировалось на **Python 3.13**).

В проекте используются **Ruff** (линтер и форматер) и **Mypy** (статический анализатор типов). Настройки находятся в `pyproject.toml`:

* Проверка кода на ошибки и стиль: `ruff check .`
* Автоматическое исправление ошибок: `ruff check --fix .`
* Сортировка импортов: `ruff check --fix --select I .`
* Форматирование кода: `ruff format .`
* Проверка типов: `mypy .`
* Полный цикл: `ruff check --fix . && ruff format . && mypy .`

**ПРИМЕЧАНИЕ:** Проверка длины строк в Ruff отключена в конфигурации (`E501`, `W505` игнорируются).

## Инструкция к запуску

1. **Клонируйте репозиторий и перейдите в директорию проекта:**
   ```bash
   git clone <URL_вашего_репозитория>
   cd <папка_проекта>
   ```

2. **Создайте и активируйте виртуальное окружение:**
   ```bash
   python -m venv .venv3
   # Для Windows (PowerShell):
   .venv3\Scripts\Activate.ps1
   # Для Linux / macOS:
   source .venv3/bin/activate
   ```

3. **Установите зависимости:**
   ```bash
   pip install -r requirements.txt
   ```

4. *(Опционально)* При необходимости переопределить имя файла базы данных создайте `.env` на основе `.env.example`:
   ```bash
   cp .env.example .env
   ```

5. **Примените миграции базы данных Alembic:**
   ```bash
   alembic upgrade head
   ```

6. **Запустите сервер FastAPI:**
   ```bash
   uvicorn main:app --reload
   ```
   *(Если порт `8000` занят системой, укажите другой порт, например: `uvicorn main:app --reload --port 8001`)*

7. **После успешного запуска сервисы будут доступны по адресам:**
   * **Базовый URL API:** http://127.0.0.1:8000
   * **Интерактивная документация Swagger UI:** http://127.0.0

8. **Очистка данных в таблицах (полный сброс БД к чистому состоянию):**
   ```bash
   alembic downgrade base && alembic upgrade head

## Проверка пользовательских сценариев

```text
После запуска проекта на http://127.0.0.1:8000 (или через Swagger UI на /docs) можно проверить все сценарии:
1. Создание бронирования:
   • Отправьте POST /bookings с валидными данными (имя от 2 до 50 символов, телефон +7XXXXXXXXXX, дата от сегодня до +30 дней, время целым часом с 12:00 до 22:00, гости от 1 до 10).
   • Сервер вернёт статус 201 Created и созданную бронь со статусом "active".
2. Защита от двойного бронирования:
   • Повторно отправьте POST /bookings на ту же дату и время.
   • Сервер вернёт 409 Conflict с телом {"detail": "Slot is already booked"}.
3. Просмотр и фильтрация броней:
   • Запрос GET /bookings вернёт все записи из базы, а GET /bookings?date=2026-11-25 отфильтрует брони только на указанную дату.
   • Запрос GET /bookings/{id} вернёт конкретную бронь или 404 Not Found ({"detail": "Booking not found"}), если ID не существует.

4. Отмена брони и освобождение слота:
• Запрос DELETE /bookings/{id} переведёт статус брони в "cancelled" без удаления записи из БД (200 OK).
• После этого повторный запрос POST /bookings на освободившиеся дату и время снова успешно создает новую активную бронь (201 Created).
```

## Описание эндпоинтов

1. **`POST /bookings`**
   * **Что делает:** Создаёт нового гостя и активную бронь на выбранные дату и время с проверкой занятости слота.
   * **Тело запроса (JSON):** `name` (`str`, 2–50 символов), `phone` (`str`, формат `^\+7\d{10}$`), `booking_date` (`date`, от сегодня до +30 дней), `booking_time` (`time`, целые часы с `12:00` до `22:00`), `guests` (`int`, от 1 до 10).
   * **Пример тела запроса:**
     ```json
     {
       "name": "Максим",
       "phone": "+79991234567",
       "booking_date": "2026-11-25",
       "booking_time": "19:00:00",
       "guests": 4
     }
     ```
   * **Ответ:** `201 Created` (`BookingCreateOut` со статусом `"active"`).
   * **Возможные ошибки:** `409 Conflict` — `{"detail": "Slot is already booked"}` (слот уже занят активной бронью), `422 Unprocessable Entity` (ошибка валидации полей).

2. **`GET /bookings`**
   * **Что делает:** Возвращает список всех бронирований (включая отменённые). Поддерживает необязательную фильтрацию по дате.
   * **Query-параметры:** `date` (`date`, опционально, формат `YYYY-MM-DD`, например `?date=2026-11-25`).
   * **Ответ:** `200 OK` (`list[BookingCreateOut]`).

3. **`GET /bookings/{id}`**
   * **Что делает:** Возвращает детальную информацию о бронировании по его идентификатору.
   * **Path-параметры:** `id` (`int`).
   * **Ответ:** `200 OK` (`BookingCreateOut`).
   * **Возможные ошибки:** `404 Not Found` — `{"detail": "Booking not found"}` (бронь с указанным ID не найдена).

4. **`DELETE /bookings/{id}`**
   * **Что делает:** Переводит статус бронирования в `cancelled` без физического удаления записи из БД, освобождая временной слот для новых гостей.
   * **Path-параметры:** `id` (`int`).
   * **Ответ:** `200 OK` (`BookingCreateOut` со статусом `"cancelled"`).
   * **Возможные ошибки:** `404 Not Found` — `{"detail": "Booking not found"}` (бронь с указанным ID не найдена).
